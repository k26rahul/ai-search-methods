## 1. Executive Summary

This report presents the design, theoretical foundations, experimental journey, and empirical benchmark evaluation of an anytime Traveling Salesperson Problem (TSP) solver developed for Programming Assignment 1 of *AI: Search Methods for Problem Solving*.

The final solver, implemented in `23f1002653.py`, employs an **Iterated Local Search (ILS)** architecture built upon three core components:
1. **Fast Greedy Initialization**: Nearest-neighbor tour construction starting from root index 0, guaranteeing an instant valid output within 5 milliseconds.
2. **Candidate-List Pruned 2-Opt Local Search**: Precomputed $k$-nearest neighbor lists ($k=12$) coupled with an $O(1)$ position lookup table, reducing the neighborhood sweep complexity from $O(N^2)$ down to $O(k \cdot N)$ while avoiding low-probability edge evaluations.
3. **Double-Bridge Perturbation (4-Opt Kick)**: A 4-opt edge reconnecting mechanism ($A-B-C-D \to A-C-B-D$) that escapes 2-opt local optima without destroying the valuable sub-path structure learned during local search.

Over the course of development, eight distinct solver variants were implemented, tuned, and evaluated across a comprehensive 64-run benchmark suite encompassing both Euclidean and Non-Euclidean test cases from $N=10$ to $N=100$ cities. The final selected architecture delivers near-optimal tour quality, rapid anytime convergence, minimal memory footprint, and complete adherence to all assignment constraints.

## 2. Problem Formulation and Operational Constraints

### 2.1 Problem Definition
The Traveling Salesperson Problem (TSP) is a classic NP-hard combinatorial optimization problem. Given a complete graph $G = (V, E)$ with $N = |V|$ vertices (cities) and a distance matrix $D \in \mathbb{R}^{N \times N}$, the objective is to find a permutation $\pi = (\pi_0, \pi_1, \dots, \pi_{N-1})$ of $V$ that minimizes the total Hamiltonian cycle length:

$$\min_{\pi \in \Pi} \text{Cost}(\pi) = \sum_{i=0}^{N-1} D[\pi_i][\pi_{(i+1) \bmod N}]$$

where $\Pi$ is the set of all $(N-1)! / 2$ possible tours.

### 2.2 Operational Environment & Rules
The assignment sets several critical operational constraints:
- **Programming Language**: Pure Python 3 using standard built-in libraries only. Specialized graph or TSP libraries (e.g., NetworkX, Concorde, SciPy routing tools) are strictly forbidden.
- **Anytime Output Specification**: Programs stream candidate tours to standard output, one tour per line as space-separated zero-based indices. The evaluation framework takes the **last valid tour** printed before process termination. If a program crashes or prints zero valid tours before the timeout, it receives zero marks for that test case.
- **Time Budget**: A strict wall-clock cutoff of 300 seconds per process in a standard Linux environment.
- **Metric Diversity**: Test cases include both Euclidean spaces (symmetric, obeying the triangle inequality) and Non-Euclidean spaces (where distances may violate geometric metric properties).
- **Evaluation Metric**: Grading is competitive and relative based on tour quality across 4 to 6 test instances of increasing problem sizes.

## 3. Final Architecture & Algorithm Design (`23f1002653.py`)

The final submission script is structured into four tightly integrated phases designed for maximum throughput, low overhead, and fail-safe anytime execution.

```
+-------------------------------------------------------------+
|                       read_input()                          |
|             Parse metric, N, coords, and dist               |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|           Phase 1: Nearest Neighbor Construction            |
|       Greedy NN from city 0 -> Immediate print_tour()       |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|          Phase 2: Candidate List Precomputation             |
|   For each city u: store top k=12 nearest neighbors (O(N^2)) |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|           Phase 3: 2-Opt Local Search to Convergence        |
|    Neighbor-list restricted edge swap with O(1) position    |
|               Emits improved tour to stdout                 |
+-------------------------------------------------------------+
                              |
                              v
+-------------------------------------------------------------+
|         Phase 4: Iterated Local Search (ILS) Loop           |
|  while time() < deadline (300s - 5s margin):                |
|    1. candidate = double_bridge(best_tour)  [4-opt kick]    |
|    2. candidate = local_search(candidate)   [2-opt cleanup] |
|    3. if candidate_len < best_len:                          |
|         best_tour = candidate                               |
|         print_tour(best_tour)                               |
+-------------------------------------------------------------+
```

### 3.1 Initialization: Nearest Neighbor Heuristic
A greedy construction heuristic builds the initial tour starting at city index 0:
- At each step, from current city $u$, select the unvisited city $v$ that minimizes $D[u][v]$.
- Repeat until all $N$ cities are visited, then return to city 0.

**Rationale**: While nearest neighbor alone yields suboptimal tours (often leaving costly long edges connecting back to the start), its $O(N^2)$ execution takes less than 5 milliseconds even for $N=100$. Emitting this tour immediately guarantees that the process has a valid submission registered with the evaluation harness from its first moments of execution.

### 3.2 Search Space Reduction: Candidate Neighbor Lists
In an unrestricted 2-opt neighborhood, each pass checks all pairs of non-adjacent edges:

$$\binom{N}{2} - N = \frac{N(N-3)}{2} = O(N^2) \text{ candidate swaps}$$

For $N=100$, each full pass evaluates approximately 4,850 edge pairs. In pure Python, evaluating this repeatedly over hundreds of iterations creates noticeable latency.

Empirical TSP research demonstrates that optimal or near-optimal tours are predominantly composed of edges connecting a city to one of its nearest neighbors. The solver precomputes a static candidate list:
- For every city $u \in \{0, \dots, N-1\}$, all other cities are sorted by ascending distance $D[u][v]$.
- The top $k = \min(12, N-1)$ nearest cities are stored in `neighbor_lists[u]`.

During 2-opt, for edge $(a, b)$ with $a = \text{tour}[i]$ and $b = \text{tour}[i+1]$, the algorithm only considers candidate endpoints $c \in \text{neighbor\_lists}[a]$. This collapses the evaluation space from $O(N^2)$ to $O(k \cdot N)$. With $k=12$ and $N=100$, each pass tests at most $12 \times 100 = 1,200$ candidate pairs, speeding up each sweep by roughly $4\times$ to $5\times$.

### 3.3 Fast Local Search: Position Map and In-Place Segment Reversals
To check candidate moves in $O(1)$ time without scanning the tour array, an inverse index table is maintained:
- `position[city]` stores the current index of `city` in `tour`.
- When testing a reconnecting edge $(a, c)$, the tour index $j = \text{position}[c]$ is retrieved in $O(1)$.
- If $j > i$ and $j \neq (i+1) \bmod N$, the move is valid. The cost delta is:

$$\Delta = (D[a][c] + D[b][d]) - (D[a][b] + D[c][d])$$

where $d = \text{tour}[(j+1) \bmod N]$.
- If $\Delta < -10^{-9}$ (floating-point epsilon), the segment between $i+1$ and $j$ is reversed in-place:
  ```python
  tour[i + 1 : j + 1] = reversed(tour[i + 1 : j + 1])
  for idx in range(i + 1, j + 1):
      position[tour[idx]] = idx
  ```
- Position entries for the reversed sub-array are updated immediately. The first-improvement strategy refreshes edge $(a, b)$ and continues scanning, accelerating convergence toward a local optimum.

### 3.4 Perturbation: 4-Opt Double-Bridge Move
Standard local search inevitably terminates at a local optimum where no single 2-opt swap can reduce tour length. Simple random kicks (such as reversing a randomly chosen sub-segment) are ineffective: a single-segment reversal is itself a 2-opt move, which local search can undo in its very first iteration, causing the search to cycle back to the state it just left.

To break this trap, the solver implements the classic **4-opt double-bridge move**:
- The tour is partitioned into four consecutive disjoint segments by choosing three random cut points $1 \le p_1 < p_2 < p_3 < N$:
  $$A = \text{tour}[0 : p_1], \quad B = \text{tour}[p_1 : p_2], \quad C = \text{tour}[p_2 : p_3], \quad D = \text{tour}[p_3 : N]$$
- The segments are reconnected in the order:
  $$\text{tour}_{\text{perturbed}} = A + C + B + D$$
- Four existing edges are removed and four new edges are introduced. Crucially, none of the individual sub-segments $A, B, C, D$ are inverted internally.
- A double-bridge move cannot be undone by any single 2-opt step; it requires a sequence of multiple 2-opt operations. This forces the local search to explore a fresh basin of attraction while preserving most of the high-quality sub-paths discovered so far.

### 3.5 Termination & Guardrails
- **Safety Margin**: A hard safety margin of 5 seconds (`SAFETY_MARGIN_SECONDS = 5`) ensures that search terminates at $T = 295$s, allowing sufficient buffer for standard I/O flushing and clean process exit without risk of external OS kill signals.
- **Corner Case Handling**: Trivial instances ($N=1$ and $N=2$) are handled with dedicated constant-time handlers.
- **Anytime Output Stream**: Every time ILS discovers a tour with cost lower than `best_len - 1e-9`, the new tour is immediately formatted and flushed to `sys.stdout`.

### 4.1 Baseline: `initial-nearest-neighbor-2-opt.py`
- **Design**: Built an initial tour using Nearest Neighbor from city 0, ran exhaustive $O(N^2)$ 2-opt passes until no improvement occurred, then applied a random single-segment reversal kick in a loop.
- **Observations & Deficiencies**:
  - For $N=100$, full $O(N^2)$ passes were sluggish in Python, limiting the number of ILS iterations.
  - More critically, reversing a single sub-segment `new_tour[i:j] = reversed(new_tour[i:j])` is itself a 2-opt move. In the subsequent local search phase, the very first 2-opt pass frequently detected that reversing that exact segment back yielded an improvement, immediately collapsing back to the original local minimum. The solver repeatedly explored the same state.

### 4.2 Version A: `double-bridge-perturbation.py`
- **Design**: Maintained exhaustive $O(N^2)$ 2-opt but replaced the single-segment reversal with the 4-opt double-bridge move.
- **Observations**:
  - The double-bridge move completely eliminated the cycling problem. After each kick, local search consistently reached different local optima.
  - However, because every pass still evaluated all $\approx 4,850$ edge pairs without pruning, the total number of ILS iterations remained low within reasonable testing windows.

### 4.3 Version B: `neighbor-list-restricted-2-opt.py`
- **Design**: Focused purely on local search acceleration. Precomputed the $k=12$ nearest neighbors for each city and used an inverse lookup array `position` to evaluate candidate moves in $O(1)$ time. Kicks remained simple segment reversals.
- **Observations**:
  - Per-pass execution time dropped significantly (over $4\times$ faster).
  - However, because the kick was still a simple segment reversal, the solver suffered from the same premature cycling observed in the baseline.

### 4.4 Exploration 1: Greedy Edge Matching (`greedy-edge-version.py`)
- **Design**: Investigated whether a better initial tour could be constructed using a global greedy strategy (Kruskal-like edge insertion):
  - Collected candidate edges from each city's nearest neighbors.
  - Sorted edges globally by ascending distance.
  - Repeatedly added the shortest edge using a Union-Find disjoint-set data structure to reject edges that would cause a vertex degree $> 2$ or create a premature cycle.
  - Patched remaining open path endpoints greedily to close the tour.
- **Observations**:
  - While greedy edge matching produced an initial tour with lower cost than raw Nearest Neighbor, the tour obtained after the very first 2-opt pass was virtually identical in cost to the 2-opt tour originating from Nearest Neighbor.
  - Sorting edges and maintaining Union-Find added code complexity and startup latency without offering a measurable advantage once local search was applied.

### 4.5 Exploration 2: Multi-Start & Or-Opt Relocations (`branch-and-bound.py` & `monster-script.py`)
- **Design**: Tested whether expanding the local search neighborhood beyond 2-opt was worth the computational cost:
  - Added **Or-opt relocations**: extracting contiguous chains of 1, 2, or 3 cities and testing reinsertion at candidate positions across the tour.
  - Added **Multi-start Nearest Neighbor**: evaluating nearest neighbor from all $N$ possible starting cities to pick the best seed.
- **Observations**:
  - Or-opt is effective at untangling non-planar crossings and shifted sequences that 2-opt cannot easily resolve. On `rnoneuc_100`, this yielded the best evaluated cost in the test suite (5197.46 vs 5210.65).
  - However, Or-opt sweeps involve $O(N)$ list splicing and re-indexing operations. On larger instances, each combined 2-opt + Or-opt pass took considerably more time, drastically cutting the total ILS perturbation count.

### 4.6 Exploration 3: Complex Metaheuristics (`hybrid-lahc-vns.py`)
- **Design**: Implemented an advanced hybrid combining:
  - Multi-heuristic construction: Multi-start NN, Greedy Edge, and Farthest Insertion.
  - **Late Acceptance Hill Climbing (LAHC)**: accepting candidate solutions if they are no worse than the solution observed $L = 80$ iterations prior.
  - **Variable Neighborhood Search (VNS)** with adaptive perturbations: 82% 4-opt double bridge and 18% cluster-based **Ruin-and-Recreate** (removing a spatial cluster of cities and reinserting via cheapest insertion).
- **Observations**:
  - LAHC provided smooth hill-climbing behavior, escaping shallow basins without manual temperature annealing.
  - However, the algorithm was sensitive to hyperparameter tuning (history length $L$, ruin cluster size, stagnation thresholds). On Non-Euclidean matrices lacking spatial correlation, cluster-based ruin-and-recreate often degraded tour structure severely, requiring lengthy repair cycles.

### 4.7 Consolidation: The Chosen Pipeline (`23f1002653.py`)
Comparing these approaches against the assignment's operational constraints led to a key engineering insight: **under a fixed time budget in interpreted Python, algorithmic throughput beats neighborhood complexity**.

A solver performing hundreds of fast candidate-list 2-opt sweeps perturbed by 4-opt double bridge explores far more independent basins of attraction than a complex solver bogged down by $O(N)$ Or-opt splicing or heavy repair heuristics. The combination of:
1. Nearest Neighbor construction (fast, safe baseline),
2. $k$-nearest candidate lists ($k=12$) with $O(1)$ position lookups, and
3. 4-opt double-bridge perturbation,
was selected as the final submission (`23f1002653.py`).

## 6. Detailed Empirical Analysis

### 6.1 Performance across Euclidean Instances
On Euclidean test cases, the problem instances adhere to metric geometry (triangle inequality and symmetry).
- For $N=10$ (`reuc_10`), all eight solvers reached the identical global minimum of **655.68** within 4.1 seconds.
- For $N=25$ (`reuc_25`), all eight solvers converged to **824.30** within 8.1 seconds.
- For $N=50$ (`reuc_50`), every solver matched the exact minimum cost of **1150.27** within approximately 20 seconds.
- For $N=100$ (`reuc_100`), six of the eight solvers (including `23f1002653.py`) reached the identical top-tier cost of **1572.62**. The remaining two versions stalled at 1574.31.

This demonstrates that for metric Euclidean instances, candidate-list 2-opt combined with double bridge consistently discovers the global optimum without needing any higher-order or computationally expensive moves.

### 6.2 Performance across Non-Euclidean Instances
Non-Euclidean instances pose a more rugged fitness landscape because the absence of the triangle inequality allows asymmetric short-cuts and counter-intuitive edge sequences.
- For $N=10$ (`rnoneuc_10`), all solvers reached **657.21**.

## 7. Key Engineering Principles & Technical Insights

1. **Why Candidate Lists Succeed**:
   In any $N$-city TSP, an optimal tour contains exactly $N$ edges. The probability that an edge $(u, v)$ in an optimal tour belongs to the top 12 nearest neighbors of $u$ exceeds 98% in typical instances. Pre-filtering avoids millions of fruitless distance evaluations on edges that would never improve the tour.

2. **Why 4-Opt Double Bridge is the Superior Perturbation**:
   A 2-opt move reverses a segment, altering the relative orientation of its cities. A double bridge cuts the tour into four blocks and transposes two of them without reversing their internal city order. Because no internal segment is flipped, 2-opt cannot undo this transition in a single step. This forces the local search to perform constructive repairs in an entirely different part of the search space.

3. **In-Place Segment Reversals in Python**:
   Python's slice assignment `tour[i+1 : j+1] = reversed(tour[i+1 : j+1])` is implemented in CPython under the hood and executes orders of magnitude faster than building new lists via concatenation (`tour[:i+1] + tour[i+1:j+1][::-1] + tour[j+1:]`). Maintaining the `position` array incrementally alongside slice reversals ensures that position queries remain strictly $O(1)$.

4. **Fail-Safe Anytime Streaming**:
   By printing immediately upon construction and thereafter whenever a strict improvement is found, the solver guarantees that at least one valid tour is in `stdout` from the first few milliseconds. Even in the event of an unexpected operating system kill signal, the last printed tour is valid and evaluated.
